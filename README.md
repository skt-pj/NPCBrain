# NPCBrain

NPCBrain is an Android research prototype for a brain-inspired NPC runtime. The long-term target is a reusable library where multiple NPCs have independent personality, memory, ongoing life state, and messaging behavior. The APK is only a demo/debug surface for observing that runtime.

## v0.3.3 scope

v0.3.3 keeps the multi-NPC conversation foundation, global Luna configuration, and the protected nine-specialist-plus-Global-Workspace cognitive topology while fixing two demo/runtime regressions.

Implemented now:

- NPC1 and NPC2 have separate personality/current-state storage and separate long-term memory.
- Three demo chat rooms exist: user + NPC1, user + NPC2, and user + NPC1 + NPC2.
- While an NPC is processing, the room shows `<name> が入力中⋯`; tapping it opens the live ten-stage public brain diagnostic view.
- Every NPC reply stores the public diagnostic trace from all nine specialist stages plus Global Workspace.
- When an NPC deliberately stays silent, the runtime now stores a `返信しませんでした` decision record with the same ten-stage trace instead of discarding the cognitive cycle.
- Silent decision records are visible for debugging and can be tapped to inspect the brain trace, but they are excluded from `recent_room_transcript` so the NPC never mistakes the debug record for an actual LINE message.
- Global AI configuration exists only on the home screen under one `AI設定` entry.
- The OpenAI API key has one input location only: home -> overflow -> AI設定.
- Individual talk screens do not expose global settings or an API-key input.
- Model ID stays `gpt-5.6-luna` while the user can choose `reasoning.effort` from `none`, `low`, `medium`, `high`, `xhigh`, or `max`.
- New brain traces persist the exact model ID and reasoning effort used for that cognitive cycle.
- OpenAI networking reuses the last Android network that successfully reached the API, then tries the normal route and other available networks.
- Only DNS / connection-establishment failures are automatically retried. Read timeouts and other ambiguous I/O failures are not blindly replayed because the POST may already have reached the API.

Not implemented yet:

- autonomous daily-life simulation;
- world clock / offline catch-up;
- scheduled activities and location/state transitions;
- spontaneous messages caused by life events;
- background execution;
- reusable Gradle library modules (`core`, `runtime`, `android`) separated from the demo app.

## Cognitive architecture

The cognitive topology remains frozen and unchanged:

1. perception / 知覚
2. salience / 注意・重要度
3. episodic_memory / エピソード記憶
4. semantic_memory / 意味記憶
5. world_model / 世界モデル・予測
6. executive_control / 実行制御・計画
7. valuation / 価値判断
8. error_monitor / 誤り監視
9. action_selection / 行動選択
10. global_workspace / 統合

Every cognitive stage uses the OpenAI Responses API with model `gpt-5.6-luna`. The reasoning effort is a runtime setting shared across the demo and supports `none`, `low`, `medium`, `high`, `xhigh`, and `max`.

Personality does not add a new brain module. Big Five traits and dynamic affective state are shared context across the existing functions. Character-specific goals, values, fears, relationships, role identity, self-beliefs, and strategies remain typed entries inside the existing semantic-memory system.

## Conversation trace contract

Each persisted conversation/debug event stores:

- `id`
- `room_id`
- `sender_id`
- `sender_name`
- `text`
- `action`
- `time_ms`
- `cause_event_id`
- `brain_trace`

Normal NPC messages use the NPC id as `sender_id`. Silent decisions use a `decision_<npcId>` sender id so they remain inspectable in the demo while `ConversationStore.recentContext()` can exclude them from actual conversational context.

Each `brain_trace` stage record includes:

- `stage_id`
- `stage_label`
- `summary`
- `confidence`
- `salient_facts`
- `personality_effect`
- `model`
- `reasoning_effort`

This is deliberately not hidden chain-of-thought. It is a concise externalized diagnostic summary generated by each stage and is suitable for debugging why a particular NPC message or silence decision was produced.

## Demo behavior

The demo treats an incoming chat message as an event, not as a request that must be answered. The NPC prompt explicitly allows silence and instructs the character not to invent unrelated off-screen events just to keep a conversation alive.

In the three-person room, NPC1 is processed first and NPC2 can see the updated recent transcript when it is processed. The demo does not recursively trigger more NPC turns, so one user message cannot create an endless NPC-to-NPC conversation.

## Home-only settings

The home screen's top-right overflow is the only settings entry point.

`AI設定` contains:

- one shared OpenAI API-key input;
- API-key configured/not-configured status;
- Luna reasoning effort selection: none / low / medium / high / xhigh / max.

The same home menu also provides NPC1/NPC2 personality and memory inspection plus demo conversation-history clearing.

The user-supplied OpenAI API key remains encrypted with Android Keystore and is not written to conversation history, NPC memory, source code, or the APK.

## UI role

The UI is intentionally a demo/debug client rather than the final product architecture. Global app settings live at the demo home level; room screens are focused on conversation and cognitive trace inspection.

The long-term architecture target is to move the NPC runtime behind a reusable API so other applications can host NPCs without depending on this demo UI.
