# NPCBrain

NPCBrain is an Android research prototype for a brain-inspired NPC runtime. The long-term target is a reusable library where multiple NPCs have independent personality, memory, ongoing life state, and messaging behavior. The APK is only a demo/debug surface for observing that runtime.

## v0.3.0 scope

v0.3.0 is the first incremental step from a single-character prompt demo toward a multi-NPC runtime.

Implemented now:

- NPC1 and NPC2 have separate personality/current-state storage and separate long-term memory.
- NPC1 intentionally reuses the v0.2.0 single-character storage for migration compatibility; NPC2 uses a namespaced store.
- Three demo chat rooms exist: user + NPC1, user + NPC2, and user + NPC1 + NPC2.
- User messages are persisted as conversation events.
- Each NPC processes a received message through the existing cognitive architecture.
- Every NPC-generated chat message stores the public diagnostic trace from all nine specialist stages plus Global Workspace.
- Tapping an NPC message opens the trace that produced that exact message: stage summary, confidence, salient facts, and personality effect.
- The main demo UI is conversation-first. The brain monitor is no longer the primary screen; it is attached to each generated message.
- A participant may stay silent. The demo performs at most one cognitive pass per NPC for each user message and does not start an autonomous NPC-to-NPC loop.

Not implemented yet:

- autonomous daily-life simulation;
- world clock / offline catch-up;
- scheduled activities and location/state transitions;
- spontaneous messages caused by life events;
- background execution;
- reusable Gradle library modules (`core`, `runtime`, `android`) separated from the demo app.

Those are planned as later incremental steps after the message/trace contract is validated.

## Cognitive architecture

The cognitive topology remains frozen and unchanged:

1. perception / 知覚
2. salience / 注意・重要度
3. episodic_memory / エピソード記憶
4. semantic_memory / 意味記憶
5. world_model / 世界モデル・予測
6. executive_control / 実行制御・計画
7. valuation / 価値判断
8. error_monitor / 誤り監視
9. action_selection / 行動選択
10. global_workspace / 統合

Every cognitive stage uses the OpenAI Responses API with model `gpt-5.6-luna` and `reasoning.effort=max`.

Personality does not add a new brain module. Big Five traits and dynamic affective state are shared context across the existing functions. Character-specific goals, values, fears, relationships, role identity, self-beliefs, and strategies remain typed entries inside the existing semantic-memory system.

## Conversation trace contract

Each NPC chat message stores:

- `id`
- `room_id`
- `sender_id`
- `sender_name`
- `text`
- `action`
- `time_ms`
- `cause_event_id`
- `brain_trace`

`brain_trace` contains one public diagnostic record per cognitive stage:

- `stage_id`
- `stage_label`
- `summary`
- `confidence`
- `salient_facts`
- `personality_effect`

This is deliberately not hidden chain-of-thought. It is a concise externalized diagnostic summary generated by each stage and is suitable for debugging why a particular NPC message was produced.

## Demo behavior

The demo treats an incoming chat message as an event, not as a request that must be answered. The NPC prompt explicitly allows silence and instructs the character not to invent unrelated off-screen events just to keep a conversation alive.

In the three-person room, NPC1 is processed first and NPC2 can see the updated recent transcript when it is processed. v0.3.0 does not recursively trigger more NPC turns, so one user message cannot create an endless NPC-to-NPC conversation.

## Personality and memory settings

The top-right overflow menu provides separate settings for NPC1 and NPC2:

- name
- Big Five traits
- role / self-image
- values
- goals
- fears
- relationships
- speech style
- long-term memory inspection

API-key configuration remains shared for the demo application. The user-supplied OpenAI API key is encrypted with Android Keystore and is not written to conversation history, memory, source code, or the APK.

## UI role

The UI is intentionally a demo/debug client rather than the final product architecture.

Primary flow:

1. choose a room;
2. send a message;
3. observe whether each NPC responds or stays silent;
4. tap an NPC message;
5. inspect the ten-stage brain trace that caused that exact message.

The long-term architecture target is to move the NPC runtime behind a reusable API so other applications can host NPCs without depending on this demo UI.
